For a long time I've been fascinated by fluid simulations as a techart problem, and frustrated with minimally-interactive fluids in so many video games. I was curious to explore the broad spectrum between *"perfect fluid simulation that runs at 2fps and cooks your GPU"* and *"boring planar water with some scrolling heightmaps on it"*. Here I'll document my journey to an interactive, texture-based fluid simulation.

Initially I was hoping to explore both 2D (texture-based) and 3D (particle-based) approaches to fluid simulation. As the month went on, it became apparent that 3D was far beyond the scope of what I could meaningfully explore in this timeframe, so I decided to focus on working in 2D. There's a surprising amount of behavior you can pull off with just 2D textures & shaders.

## Double-Buffering and Self-Drawing
(talk more about setting up shit here. took a bit to even get basic drawing-to-texture-persistently working. maybe jut how the baic)

The first problem you'll run into when trying to stand up some sort of self-iterative (? right word?) shader is that generally its not a good idea to write to the same texture you're reading from in a shader. At least in Godot, you can't just tell a DrawableTexture to blit to itself, and even if you could it would be a bad idea because of race conditions as a result of GPU parallelism. If each pixel cares about the state of other pixels (i.e. its neighbors), then for some pixels you'll be reading previous-frame's data, and for others youll be reading next-frames data that you wrote to in this pass. Bad idea on all fronts. (NOTE that this is not a hard limitation w/ compute shaders and approaches like red-black checkerboard parallelism avoid race conditions, but that doesnt matter here. it's illegal in typical shaders and textures!)

The solution is **double-buffering**, or ping-pong buffering. Essentially you have two textures that play leapfrog with one another, each taking turns being the "next" and the "previous". (expand on this? visual?)

## Cellular Automata

(do we bother explaining what cellular automata is?)
<br>
If you've not heard of "cellular automata", put simply it involves 1) a grid of some data, and 2) a simple ruleset for how each grid's data changes with each "step", typically based on neighboring grid data. It's a great way to see how simple low-level rules can give rise to complex emergent behavior. See: Conways Game of Life as probably the most popular example.

My first goal was to implement some sort of texture-space motion effect using cellular automata, just as a proof-of-concept for self-iterating textures & shaders. Before seeing what existing solutions are out there, I decided to try to write my own from first principles, to very limited effect. 

<video src="../../../assets/images/fluids/lateral_walk.mp4" autoplay muted loop controls width="100%"></video>

I figured the simplest version of this was some sort of pixel-walk shader, where the current pixel looks at a neighbor pixel (here, the next one to the left) and simply writes that neighbor pixel's value to the current pixel's value. 

```glsl
vec4 smear_walk(vec2 uv) {
  float pixel_size = get_pixel_size(); // custom utility function to get UV width of a pixel
  return texture(previous_texture, uv + vec2(pixel_size, 0));
}
```

This results in a simple scrolling effect, a bit like a very simple river or conveyor belt. Next I wanted more authorial control over the direction of flow.

---

<video src="../../../assets/images/fluids/heightmapwalk_radial.mp4" autoplay muted loop controls width="100%"></video>
This one has values walk down a "heightmap" texture. Each pixel looks at its "height" on the heightmap, and its neighboring pixel's "height" on the heightmap. It then takes any pixels that share the highest local elevation (in case more than one share the spot for "highest") and averages them out with the current value of the pixel.
<br><br>
There are a number of other ways this "walking down slope" could be done differently (i.e. we could sample diagonals, we could do without the averaging, use a more sophisticated algorithm to determine the slope).

```glsl
vec4 heightmap_walk(vec2 uv) {
  float pixel_size = get_pixel_size();
  vec2[] neighbor_UVs = {
    uv + vec2(0,  pixel_size), 	// up
    uv + vec2(0, -pixel_size),	// down
    uv + vec2(-pixel_size, 0), 	// left
    uv + vec2( pixel_size, 0)	// right
    };
  float current_height = texture(height_gradient, uv).r;
  float[] neighbor_heights = {
    texture(height_gradient, neighbor_UVs[0]).r,
    texture(height_gradient, neighbor_UVs[1]).r,
    texture(height_gradient, neighbor_UVs[2]).r,
    texture(height_gradient, neighbor_UVs[3]).r
  };
  float max_height = max(current_height, 
    max(neighbor_heights[0], 
    max(neighbor_heights[1], 
    max(neighbor_heights[2], 
        neighbor_heights[3]))));
  float new_value = texture(previous_texture, uv).r;
  float num_contributors = 1.0;
  // take the average of current pixel's value and the values of the highest neighbors
  for (int i = 0; i < 4; i++)
  {
    if (neighbor_heights[i] == max_height)
    {
      num_contributors++;
      new_value += texture(previous_texture, neighbor_UVs[i]).r;
    }
  }
  new_value /= num_contributors;
  return vec4(new_value);
}
```

I also implemented a very simple neighbor-blur to roughly simulate diffusion over time, somewhat similar to how a gas might diffuse.

```glsl
vec4 neighbor_blur(vec2 uv) {
  float pixel_size = get_pixel_size();
  return (
    texture(previous_texture, uv + vec2( pixel_size, 0)) +
    texture(previous_texture, uv + vec2(-pixel_size, 0)) + 
    texture(previous_texture, uv + vec2(0,  pixel_size)) + 
    texture(previous_texture, uv + vec2(0, -pixel_size))
    ) / 4.0;
}
```

This video was a great introduction to core fluid simulation concepts, however I confess to have been a bit overwhelmed at the prospect of replicating his work. There's certainly a lot of shader code there, and I didn't want to just copy a huge volume of code wholecloth without understanding what it was doing. His simulation is also extremely realistic, and I was curious if there was a simpler algorithm that might not perfectly model real fluid behavior, but would still *feel* like it does while being much more performant.
<br><br>
I eventually landed on [this article by Andy Green](https://andytech.art/playing-with-runtime-fluid-simulation), which offers peek at several approaches for simple, performant & constrained implementations of "fluid-y" behavior that, while not strictly realistic, are still interactive & responsive to the game world. 
<br><br>
In his article, Andy Green references Wyatt Flanders' "Me And My Neighborhood" [shadertoy](https://www.shadertoy.com/view/WtsSz2) and [PDF explainer](https://wyattflanders.com/MeAndMyNeighborhood.pdf), which is such an elegantly minimalist implementation and explanation of fluid simulation. I shamelessly made a shader based on it, with some subtle modifications to suit Godot's GLSL (i.e. bilinear filtering and 0...1 UVs instead of integer pixel coords).

<video src="../../../assets/images/fluids/shadertoy_fluid_mixing.mp4" autoplay muted loop controls width="100%"></video>

This simulation is not perfect, in some ways that are apparent here. You might notice for example that some areas become more black than the base black initial color of the texture - this is because this simulation allows for "negative" fluid mass, and outputting a negative color value in a lit surface shader appears to cut into diffuse lighting. 
<br><br> 
That said, this shader is perfect for what we're doing here. Its interactive and it moves in a way that feels fluidic, even featuring emergent vortices. It's also very easy to read (for a fluid sim) and each part does a very clear job, making it much easier to start messing with different properties to try to get different behavior to happen. Below I've put Wyatt's fluid sim as I've modified it to work in a Godot blit shader, in case anyone wants to build on it (blend_disabled and filter_linear are necessary for this to work well!)

```glsl
shader_type texture_blit;
render_mode blend_disabled;

uniform sampler2D previous_texture : hint_blit_source0, filter_linear, repeat_disable;

float get_pixel_size() {
  return 1.0 / float(textureSize(previous_texture, 0).r);
}

// Fluid sim by Wyatt Flanders
// PDF explainer  : https://wyattflanders.com/MeAndMyNeighborhood.pdf
// Shadertoy      : https://www.shadertoy.com/view/WtsSz2
vec4 fluid_sim_read_field(vec2 uv)
{
  // Rule 1 : All My Energy transates with my ordered Energy
  vec2 velocity = texture(previous_texture, uv).xy;
  vec2 position_guess = uv - velocity * get_pixel_size(); // reverse advection
  return texture(previous_texture, position_guess); 
}

vec4 fluid_sim_from_shadertoy(vec2 uv)
{
  vec4 Energy = fluid_sim_read_field(uv);
  vec4 pX = fluid_sim_read_field(uv + vec2(1,0) * get_pixel_size());
  vec4 pY = fluid_sim_read_field(uv + vec2(0,1) * get_pixel_size());
  vec4 nX = fluid_sim_read_field(uv - vec2(1,0) * get_pixel_size());
  vec4 nY = fluid_sim_read_field(uv - vec2(0,1) * get_pixel_size());
  // Rule 2 : Disordered Energy diffuses completely (accumulate pressure?)
  Energy.b = (pX.b + pY.b + nX.b + nY.b)/4.0;
  // Rule 3 : Order in the disordered Energy creates Order ()
  vec2 Force;
  Force.x = nX.b - pX.b;
  Force.y = nY.b - pY.b;
  Energy.xy += Force/4.0;
  // Rule 4 : Disorder in the ordered Energy creates Disorder :
  Energy.b += (nX.x - pX.x + nY.y - pY.y)/4.;
  // Gravity effect :
  Energy.y -= Energy.w/300.0;  
  // Mass conservation :
  Energy.w += (nX.x*nX.w-pX.x*pX.w+nY.y*nY.w-pY.y*pY.w)/4.;  
  //Boundary conditions :
  float boundary_size_px = 16.0;
    if(
    uv.x < get_pixel_size()			* boundary_size_px || 
    uv.y < get_pixel_size()			* boundary_size_px || 
    uv.x > 1.0 - (get_pixel_size()	* boundary_size_px) ||
    uv.y > 1.0 - (get_pixel_size()	* boundary_size_px) )
    {
      Energy.xy *= 0.;
    }
  return Energy;
}

void blit() {
  COLOR0 = fluid_sim_from_shadertoy(UV);
}
```

One technique this sim uses is called **reverse advection**, a technique a lot of grid-based fluid sims use to simulate motion. Each grid cell in this sim stores its velocity, pressure, and (roughly)mass. Your first reflex when writing a fluid sim might be to take each grid cell's velocity, and "push" that cells data to another cell based on that velocity. This would be **forward advection** - advection meaning the movement of a quantity in a fluid.
<br><br>
Unfortunately, shaders don't work like that. A fragment/pixel shader is designed to write to the current pixel, a constraint imposed by GPU parallel processing of pixels. You can't just jump to another pixel position and write data to it in a shader - even if you could, you would run into race conditions where other "source" pixels might want to write to that "destination" pixel. "Scatter" operations - operations that take **this pixel** and throw it to some arbitrary other pixel - are not possible to do in typical shaders. (An exception is compute shaders, but we aren't doing that right now!) 
<br><br>
Instead, we can take the velocity in our pixel, trace it backwards along the negative of our velocity to get "the pixel where this pixel used to be", and pull its values into **this pixel.** This is reverse advection, and it is a "gather" operation (operations that take arbitrary other pixels and pull them into this pixel) which is much more compatible with a typical shader.
